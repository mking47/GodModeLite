# 原版「上帝模式」逆向分析报告

> 分析对象：`/root/workspace/gm.apk`（上帝模式 / GodMode，作者 jrsen，基于 kaisar 的 Xposed 模块）
> 材料：`apk_ext/`（dex、resources.arsc、res/、assets/xposed_init）、`smali_out/classes{,2}`（baksmali 全量 smali）、`res_dump.txt`（aapt2 dump resources 全量）、`analysis/manifest_dump.txt`（aapt2 dump badging / permissions / xmltree 实测输出）
> 说明：本报告每条结论都标注了证据来源（smali 文件:行 / 资源 id / manifest 行号 / 常量）。`AndroidManifest.xml` 已由 `analysis/manifest_dump.txt` 实测解码，第 1 节全部为实测值；仅个别"运行时行为/意图"标注 `【推断】`。

---

## 0. 结论速览

1. 它不是一个"权限更高"的 App，而是**一个 Xposed 模块 + 一个跑在 system_server 里的 Binder 服务**。核心能力全部来自 Xposed：在目标进程里 hook `Activity`/`View`/`assets`，直接把别人的 View 设为 `INVISIBLE`/`GONE`。
2. 规则数据落在 `/data/system/godmode/`（system_server 身份写入，权限 0777），UI 进程**读不到**，只能通过 Binder 拿 `ParcelFileDescriptor`（`openImageFileDescriptor`，且强制校验路径前缀 + `.webp` 后缀）。
3. 规则模型是三层 `HashMap`：`AppRules{pkg → ActRules{activityClass → List<ViewRule>}}`，Gson 序列化；单个 App 一个 `<pkg>.rule` 文件（pretty print JSON）。
4. 备份是 **普通 ZIP**（不是 gzip，尽管文件名后缀是 `.gzip`），内含扁平化的 `manifest.json` + N 个 `<毫秒时间戳>.webp`，通过 SAF（`CreateDocument`/`OpenDocument`）写出读入。
5. 交互上最有价值、且完全可以在免 Xposed 版本复刻的是：**「长按 → 命中 View → 高亮蒙版 → 可拖动/可取消/粒子爆炸 → 生成规则」**这一整套 UI 流程与规则数据格式。

## 2. 工作原理

### 2.1 模块入口

`apk_ext/assets/xposed_init` 唯一一行：

```
com.kaisar.xposed.godmode.injection.GodModeInjector
```

`GodModeInjector` 实现 `IXposedHookLoadPackage` + `IXposedHookZygoteInit`（`injection/GodModeInjector.smali:6-7`）：

- `initZygote(StartupParam)`：保存 `modulePath`；`XModuleResources.createInstance(modulePath, null)` 生成 `moduleRes`（`GodModeInjector.smali:1010-1027`）。
- `handleLoadPackage(lpp)`：**两句分叉**（`GodModeInjector.smali:894-1008`）
  - `lpp.packageName.equals("android")` → 这是 system_server：
    ```
    XServiceManager.initForSystemServer();
    XServiceManager.registerService("godmode", fetcher);   // fetcher 里 new GodModeManagerService(context)
    ```
  - 其他进程（且 `isFirstApplication`）：hook `Activity.onCreate`（注入模块资源）→ `registerHook()` → `GodModeManager.getDefault().addObserver(packageName, new ManagerObserver())` → `switchProp.set(isInEditMode())` → `actRuleProp.set(getRules(packageName))`。

### 2.2 XServiceManager：把「服务」塞进 system_server

`injection/bridge/GodModeManager.getDefault()` 里 `XServiceManager.getService("godmode")`（`injection/bridge/GodModeManager.smali:41-44`）。`XServiceManager` 的做法很巧（`com/kaisar/xservicemanager/XServiceManager.smali`）：

1. `initForSystemServer()`：反射拿 `android.os.ServiceManager.getIServiceManager()`，用 `Proxy.newProxyInstance` 包一层 InvocationHandler（`XServiceManager.smali:452-579`）。
2. 拦截 `addService`，且服务名等于 **`"clipboard"`** 时，把 clipboard 的 binder 换成 `BinderDelegateService(clipboardBinder, XServiceManagerService)`（`XServiceManager.smali:687-741`；常量 `DELEGATE_SERVICE="clipboard"`、`TRANSACTION_getService=0x5f58534d`）。
3. 任何进程调用 `getService("godmode")`：反射 `ServiceManager.checkService("clipboard")` 拿 binder，然后 `transact(0x5f58534d, parcel(接口名, 服务名))`，`XServiceManagerService`（活在 system_server）返回真正的 `IBinder`（`XServiceManager.smali:153-288`）。
4. `registerService(name, fetcher)` 只在 system_server 生效，`fetcher.createService(ActivityThread.getSystemContext())` 直接用**系统 Context** 实例化服务（`XServiceManager.smali:861-913,687-741`）。

⇒ 于是 `GodModeManagerService` 是**运行在 system_server 进程里的对象**，`Environment.getDataDirectory()+"/system/godmode"` = `/data/system/godmode` 对它可写（`GodModeManagerService.smali:60-95,436-494`）。这就是为什么原版不需要 root 也能把规则写到 `/data/system`。

### 2.3 Hook 点清单（`registerHook()`，`GodModeInjector.smali:656-890`）

| # | 目标 | 方法 | 做法 |
|---|---|---|---|
| 1 | `Activity` | `onCreate(Bundle)` | after：`injectModuleResources(activity.getResources())`（`GodModeInjector$1.smali:49-53`）——让目标进程能 `getString` 模块的字符串 |
| 2 | `Activity` | `onPostResume()` / `onDestroy()` | `ActivityLifecycleHook`：resume 时 `ViewSelector.setTopActivity(activity)`、给 `decorView` 注册 `OnGlobalLayoutListener`；destroy 时移除（`hook/ActivityLifecycleHook.smali:82-224`） |
| 3 | `android.os.SystemProperties` | `native_get_boolean(String,boolean)`（SDK<29） | `SystemPropertiesHook`：编辑模式下把所有 `"debug.layout"` 查询强制返回 `true`（`hook/SystemPropertiesHook.smali:36-69`） |
| 4 | `android.os.SystemProperties` | `native_get`（SDK>=29，`hookAllMethods`） | `SystemPropertiesStringHook`：同上，返回 `"true"` |
| 5 | `android.sysprop.DisplayProperties` | `debug_layout()` | `DisplayPropertiesHook`：返回 `Optional.of(true)`（`hook/DisplayPropertiesHook.smali:36-59`） |
| 6 | `SystemProperties` | `callChangeCallbacks()` | 属性变化监听器里主动调一次，让已存在的窗口立即重绘调试线（`SystemPropertiesHook.smali:71-96`） |
| 7 | `ViewGroup` | `onDebugDrawMargins(Canvas,Paint)` | `XC_MethodReplacement.DO_NOTHING` —— 把系统调试边距绘制干掉，自己画（`GodModeInjector.smali:794-812`） |
| 8 | `ViewGroup.onDebugDraw(Canvas)` / `View.debugDrawFocus(Canvas)` | 用 `GodModeInjector$2`：`view.getTag()=="gm_cmp"` 时 `setResult(null)`，即**跳过自己覆盖层**（`GodModeInjector$2.smali:35-62`） |
| 9 | `View` | `dispatchTouchEvent(MotionEvent)` | `EventHandlerHook`：编辑模式下接管所有触摸（长按选中、拖动移动蒙版、松手落规则） |

关键点：**它复用了系统自身的"显示布局边界"(debug.layout) 通道来高亮控件**——通过 hook 属性查询把 `debug.layout` 变成 true，系统就会在每个 View 上画调试框；再用 `onDebugDraw`/`onDebugDrawMargins` 接管绘制细节。这既是"选中高亮"的本体，也是为什么它对 `com.android.systemui`、桌面、`com.android.settings`、输入法做了黑名单（否则会全局画框/递归出错）。

`checkBlockList(pkg)`（`GodModeInjector.smali:92-285`）拦：
- `com.android.systemui`、`com.android.settings`；
- 所有 `ACTION_MAIN + CATEGORY_HOME` 的桌面；
- 所有 `android.view.InputMethod` 输入法；
- 没有任何 Activity 的包。

### 2.4 「长按选中控件」的完整链路

1. 编辑模式开启：`switchProp`（`Property<Boolean>`）→ `EventHandlerHook.mIsInEditMode=true`；同时 `ViewSelector.setPanel(true)`（`GodModeInjector.smali:584-643`）。
2. `View.dispatchTouchEvent` 被 hook（`hook/EventHandlerHook.smali:1059-1203`）：
   - `ACTION_DOWN`：先判断是否多指（`mMultiPointLock` → Toast `"不支持多点操作"`，`EventHandlerHook.smali:492`）；再用 `isAttachedToActivity(view)`（反射 `ViewRootImpl.mWindowAttributes.type == TYPE_BASE_APPLICATION`）判断是否属于 Activity 窗口，否则 Toast `"该控件属于悬浮窗暂不支持编辑"`（`EventHandlerHook.smali:520,736-777`）；
   - 通过后 `ViewSelector.updateSelectedView(view)`、`requestDisallowInterceptTouchEvent(true)`、记录 `mDeltaX/mDeltaY`，并 `mHandler.postDelayed(new CheckForLongPress(view), ViewConfiguration.getLongPressTimeout())`（`EventHandlerHook.smali:591-608`）；
   - `ACTION_MOVE`：长按成立后拖动蒙版：`MaskView.updateOverlayBounds(rawX-dx, rawY-dy, w, h)`，并与 `CancelView.getRealBounds()` 求交 → `setMarked(是否命中取消区)`（`EventHandlerHook.smali:617-682`）；
   - `ACTION_UP/CANCEL`：移除长按计时；若 `mMarked` → `performDetachMirrorView`（进入"爆炸"动画），否则恢复。
3. `CheckForLongPress.run()`：`performAttachMirrorView(view)` + `view.performHapticFeedback(0)`（`EventHandlerHook$CheckForLongPress.smali:64-123`）。
4. `performAttachMirrorView(view)`（`EventHandlerHook.smali:779-920`）：
   - `CancelView`（一个自绘 View，画"拖到此处取消"区域与文案）`attachToContainer(decorView)`；
   - `MaskView.makeMaskView(ctx)` → `setMaskOverlay(view)` → `setMarkColor(MARK_COLOR=0xff 0x96 0x8b:0xc3 0x4b)` → `updateOverlayBounds(...)` → `attachToContainer(decorView)`；
   - `ViewHelper.snapshotView(topParent)` 截图（给粒子爆炸用）；
   - `ViewHelper.makeRule(view)` 生成 `ViewRule`；
   - `ViewController.applyRule(view, rule, false)` **立刻隐身**（所见即所得）。
   颜色常量：`MARK_COLOR = Color.argb(0x96,0x8b,0xc3,0x4b)`（半透明绿），`OVERLAY_COLOR = Color.argb(0xff,0,0,0)`（`EventHandlerHook.smali:80-110`）。
5. `performDetachMirrorView(view)`：若未命中取消区 → `ParticleView(duration=1000ms).boom(maskView)` 把蒙版"炸"成粒子（`hook/EventHandlerHook.smali:1016-1051`），`ParticleView$OnAnimationListener.onAnimationEnd` 里把规则交给 `ViewSelector` 落盘（`EventHandlerHook$1`）；若命中取消区 → `ViewController.revokeRule` 撤销。
6. 音量键选择（给"点不到"的控件用）：`Activity.dispatchKeyEvent` 分支里 `KEYCODE_VOLUME_UP/DOWN`（0x18/0x19）在编辑模式下切换 `mViewNodes` 索引（`ViewHelper.buildViewNodes(decorView)`），实时更新蒙版边界（`EventHandlerHook.smali:234-466`）。→ 注意：`registerHook()` 只把 `EventHandlerHook` 挂到 `View.dispatchTouchEvent`，`dispatchKeyEvent` 分支是**该方法内的分支**，实际触发路径见 `ViewSelector` 里对 `dispatchKeyEvent` 的引用（`ViewSelector.smali:119`），属"按键选择"备用通道。

### 2.6 规则如何回传给本应用（Binder 机制）

跨进程契约 `IGodModeManager`（AIDL，12 个方法，`IGodModeManager.smali`）：


- 客户端：`injection/bridge/GodModeManager`（单例，`mGMM` 为空则用 `IGodModeManager$Default` 空实现，`GodModeManager.smali:27-93`）；本 App 的 UI 与目标进程都走它；`repository/LocalRepository` 只是三行转发（`LocalRepository.smali:16-42`）。

- 落盘队列：`HandlerThread("work-thread")` + `Handler.Callback`，消息码
  `WRITE_RULE=2`、`DELETE_RULE=4`、`DELETE_RULES=8`、`UPDATE_RULE=0x16(22)`（`GodModeManagerService.smali:22-32,1493-1776`）：
  - 2：`saveBitmap(bitmap, appDir)` → `<ms>.webp` → 写进 `ActRules[activityClass]` list → Gson pretty → `<pkg>.rule` → 通知观察者；
  - 4：删图片文件 + 从 list 移除 + 重写文件（空则删整个 app 目录）；
  - 8：直接 `FileUtils.delete(appDir)` 并广播空 `ActRules`；

- 目标进程侧回写：`ManagerObserver`（`IObserver$Stub`）在主线程 Handler 上转成 `GodModeInjector.notifyEditModeChanged/notifyViewRulesChanged`（`bridge/ManagerObserver.smali`）；`ActivityLifecycleHook.onPropertyChange(ActRules)` 做**差量同步**：先 `removeAll` 旧规则、`revokeRuleBatch` 撤销，再用新表 `applyRuleBatch` 应用（`hook/ActivityLifecycleHook.smali:226-483`）。
- 权限校验：`enforcePermission(...)` → `checkPermission(pkg)`：`Binder.getCallingUid()` → `getPackagesForUid()` 里是否含 `"com.viewblocker.jrsen"`（或目标包名），否则抛 `RemoteException`（`GodModeManagerService.smali:196-306`）。`writeRule/deleteRule` 允许「目标 App 自己」或本模块（`GodModeManagerService.smali:2102-2119`）。
- `openImageFileDescriptor(path)`：**这是 UI 进程能看缩略图的唯一途径**。校验 `path.startsWith(/data/system/godmode)` 且以 `.webp` 结尾，`ParcelFileDescriptor.open(file, MODE_READ_ONLY)`，否则抛 `RemoteException("unauthorized access %s")`（`GodModeManagerService.smali:1795-1876`）。

### 2.7 目标应用资源注入

`injectModuleResources(Resources)`（`GodModeInjector.smali:296-582`）：先用 `resources.getString(0x951200b6)`（`res_inject_success = "Resources injection success"`）探测是否已注入；未注入则 `AssetManager.addAssetPath(modulePath)`（反射），再 `getString(...)` 验证；失败抛/记日志（`Fatal: injectModuleResources: test injection failure!`）。注入成功后目标进程才能用 `moduleRes` 解析模块布局（`ViewSelector.showNodeSelectPanel` 里 `moduleRes.getLayout(layout_node_selector)`，`injection/ViewSelector.smali:485-493`）。

### 3.1 `rule/ViewRule`（`Parcelable` + `Cloneable`，20 个字段）

`label=loadLabel`、`packageName=ctx.getPackageName()`、`matchVersion*=getPackageInfo(...,0)`、`versionCode=23`、`imagePath=""`、`alias=` text 或 contentDescription（两者都空则 `""`）、`x/y=getLocationInWindow`、`w/h=getWidth/Height`、`depth=getViewHierarchyDepth`、`activityClass=getComponentName().getClassName()`、`viewClass=view.getClass().getName()`、`resourceName=getResourceName(id)`（id 为 -1 时为空）、`text=TextView.getText()`、`description=getContentDescription()`、`visibility=4`、`timestamp=now`。

### 3.3 磁盘布局与序列化

`GodModeManagerService` 常量（`service/GodModeManagerService.smali:18-32`）：

```
BASE_DIR   = String.format("%s/system/%s", Environment.getDataDirectory(), "godmode")   // /data/system/godmode
CONFIG_FILE_NAME = "conf"      IMAGE_FILE_SUFFIX = ".webp"      RULE_FILE_SUFFIX = ".rule"
```

实际磁盘结构：

```

├── conf                                  (空文件，仅创建/chmod 0777；loadRuleData 未读它)
└── <pkg>/
    ├── <pkg>.rule                        (Gson prettyPrint 的 ActRules JSON)

    └── ...
```

- 目录/文件创建后统一 `FileUtils.setPermissions(f, 0777, -1, -1)`（`setPermissions(File,int,int,int)`，见 `getBaseDir/getAppDataDir/getAppRuleFilePath/saveBitmap`），目的是让 UI 进程与目标进程也能读。
- `.rule` 内容 = `ActRules` 的 JSON（`Map<activityClass, List<ViewRule>>`），**写入用 `new GsonBuilder().setPrettyPrinting().create().toJson(actRules)`**（`GodModeManagerService.smali:1539-1561,1647-1669,1732-1755`）。

- UI 侧另有偏好存储：`PreferenceManager.getDefaultSharedPreferences`（`pref_general.xml` 里的 `editor_switch` 等）与 `getSharedPreferences("settings")` 的 `version_code`（`GeneralPreferenceFragment.smali:765-791`）。**编辑模式本身不持久化**到 `mInEditMode`（进程重启后 `isInEditMode()` 为 false，UI 靠 `editor_switch` 记住开关状态）。

### 4.1 常量与入口


入口：

  （注：`menu_backup_rules`="备份全部规则"、`menu_delete_rules`="删除全部规则" 是字符串资源，但**本版本 UI 只实现了单 App 备份**：`backupRules(uri, packageName, rules)` 的签名只带一个包名。）
- 备份执行：`SharedViewModel.backupRules(Uri, String pkg, List<ViewRule>, ResultCallback)` → 线程池 → `BackupUtils.backupRules(...)`，异常包成 `BackupUtils$BackupException`，主线程回调 `ResultCallback.onSuccess/onFailure`（`model/SharedViewModel.smali:169-206,297-333`）。
- 恢复执行：`SharedViewModel.restoreRules(Uri, ResultCallback)` → `BackupUtils.restoreRules(uri)`，异常 `RestoreException`（`SharedViewModel.smali:350-416,403-416`）。

### 4.2 备份流程（`BackupUtils.backupRules`，`util/BackupUtils.smali:33-438`）

1. 临时目录 `getCacheDir()/backup`；已存在则 `FileUtils.rmdir` 后 `mkdirs()`，失败抛 `BackupException("Create backup directory failed.")`。
2. 遍历传入的 `List<ViewRule>`，对每条：
   - `ViewRule copy = rule.clone()`；
   - `GodModeManager.getDefault().openImageFileDescriptor(rule.imagePath)` 拿 `ParcelFileDescriptor`（**只能通过 system_server 侧读图**）；
   - 目标文件名 = `System.currentTimeMillis() + ".webp"`，`FileChannel.transferTo(0, size, out)` 复制；
   - `copy.imagePath = 新文件名`（**只存相对文件名，不存绝对路径**），把新文件路径加入待打包列表；
   - 无论有没有图片，`copy` 都会加入待序列化列表。
3. 写 `cache/backup/manifest.json`（Gson `JsonObject` 手工构造，`BackupUtils.smali:301-352`）：

```json
{
  "version": 1,
  "packageName": "被备份的包名",
  "rules": [ { ...ViewRule JSON..., "img_path": "1699999999123.webp" }, ... ]
}
```

4. 打开 SAF 输出流 `getContentResolver().openOutputStream(uri)`，调用 `ZipUtils.compress(out, paths[])`；`paths` 里含 `manifest.json` 与所有 webp 的**绝对路径**。
5. finally：`FileUtils.rmdir(cache/backup)` 清理。

生成的文件名由 UI 侧拼：`String.format("%s_%s.gzip", appLabel, new SimpleDateFormat("yyyy-MM-dd_HHmmss", Locale.getDefault()).format(new Date()))`（`ViewRuleListFragment.smali:420-482`），即形如 `微信_2023-11-12_103045.gzip`。

### 4.3 打包格式（`util/ZipUtils`）

`ZipUtils.compress(OutputStream, String... files)`（`util/ZipUtils.smali:16-132`）：

```java
ZipOutputStream zos = new ZipOutputStream(out);
for (String p : files) {
    File f = new File(p);
    zos.putNextEntry(new ZipEntry(f.getName()));   // 只用 basename，扁平结构
    FileUtils.copy(new FileInputStream(f), zos);
    zos.closeEntry();
}
```

`ZipUtils.uncompress(InputStream, String dir)`（`util/ZipUtils.smali:134-235`）：`ZipInputStream` 逐 entry，`new File(dir, entry.getName())` 写文件（**没有 zip-slip 校验**，`../` 会逃逸）。

⇒ **后缀是 `.gzip`，内容其实是标准 ZIP（ZipOutputStream / deflate）**；用 `unzip -l` 就能看到 `manifest.json` + 若干 `.webp`。**不是 GZIP 流**。

### 4.4 恢复流程（`BackupUtils.restoreRules`，`util/BackupUtils.smali:440-699`）

1. 临时目录 `getCacheDir()/restore`（先 `rmdir` 再 `mkdirs`，失败抛 `RestoreException("Create restore directory failed.")`）。
2. `getContentResolver().openInputStream(uri)` → `ZipUtils.uncompress(in, cache/restore)`。
3. `cache/restore/manifest.json` 不存在 → `RestoreException("Miss manifest.json file.")`。
4. `FileUtils.readTextFile` → `new GsonBuilder().create().fromJson(json, JsonObject.class)`。
5. 逐字段读：`version`（`getAsInt()`，**读完丢掉，不做比较**）、`packageName`（`getAsString()`，**丢弃**）、`rules`（`getAsJsonArray`）。⚠️ 也就是说：**VERSION 常量仅用于写，恢复端没有任何版本校验**；包名以每条规则自带的 `package_name` 为准。
6. 对 `rules` 中每条：
   - `gson.fromJson(element.toString(), ViewRule.class)`；
   - `Bitmap bmp = BitmapFactory.decodeFile(new File(cache/restore, rule.imagePath).getPath())`（相对文件名拼回临时目录）；
   - `GodModeManager.writeRule(rule.packageName, rule, bmp)` → 走 2.6 的 `WRITE_RULE` 队列；
   - `CommonUtils.recycleNullableBitmap(bmp)`。
7. finally 清理 `cache/restore`。

**合并 / 替换语义**：`writeRule` 是 `ActRules[activityClass].add(rule)`（`GodModeManagerService.smali:2094-2213`），**追加（append / merge）而不是替换**；不会清空该 App 已有规则。同一条规则重复恢复会在 list 里出现重复项（`applyRule` 的 `blockedViewCache` 用 `rule.hashCode()` 去重，表现为"已屏蔽（Skipped）"而不是报错，见 `ViewController.smali:396,414` 的 `[Success]/[Skipped]/[Failed]` 日志）。要"替换"必须先"删除全部规则"（itemId `0x7f95011a` → `SharedViewModel.deleteAppRules(pkg)` → `DELETE_RULES`）。

## 7. 结论：能不能"照搬"，以及免 Xposed 版能做到什么

### 7.1 为什么"普通应用 + root"不能像它那样在别人进程里移除 View

这是本报告最重要的一条工程结论：

1. **View 是进程内对象，跨进程没有句柄**。`ViewController.applyRule(view, rule, ...)` 拿的是**目标进程堆里的 `View` 引用**（`injection/ViewController.smali:70-261`），并对它调 `setAlpha/setClickable/setVisibility/requestLayout`。一个第三方 App 拿不到别人进程的对象引用，root 也拿不到——root 只给你文件系统与 `ptrace`/`su` 的能力，**没有一个稳定的 API 能"远程调用另一个进程里的 View 方法"**。
2. **无障碍（AccessibilityService）只是"读/点"**。`AccessibilityNodeInfo` 有 `ACTION_SCROLL/CLICK/SET_TEXT`、`performAction` 等有限动作；**没有 `setVisibility`/`removeView`**，也没有"任意方法调用"。而且节点树里 `INVISIBLE` 的控件默认不下发（`includeNotImportantViews`、`FLAG_INCLUDE_NOT_IMPORTANT_VIEWS` 也拿不到真正的 `GONE`），所以"先隐藏再读"是不可逆的。
3. **它之所以能做到，是因为 Xposed 把模块代码注入目标进程**：`handleLoadPackage` 在每个目标进程里跑（`GodModeInjector.smali:894`），所以 `ActivityLifecycleHook` 能拿到 `Activity` 实例、`EventHandlerHook` 能 hook `View.dispatchTouchEvent`、`ViewController` 能直接改 View。等价于"在目标进程里执行了我们的代码"。
4. **悬浮窗覆盖（`TYPE_APPLICATION_OVERLAY`）只能"盖住"，不能"移除"**：盖一层不透明 View 只是视觉遮挡，底下的 View 仍在布局里占位、仍可点（除非覆盖层吃掉触摸）、仍会被无障碍/截图/自动化看到。`GONE` 与 `INVISIBLE` 的差别（占位/不占位）悬浮窗**一个都做不到**。
5. **root 能做的是"改系统层面的显示"**，不是"改别人 App 的 View"。例如改 `debug.layout`（`setprop debug.layout true`，正是原版 hook 的那个属性）能让系统全局画布局框——但这只影响绘制，不移除控件。

### 7.2 可以照搬的部分（强烈建议照搬）

| 可照搬项 | 具体内容 |
|---|---|
| **规则数据模型** | `ViewRule` 的 20 个字段名/JSON 名（`package_name/act_class/view_class/res_name/text/description/depth/x/y/width/height/visibility/img_path/alias/timestamp/match_version_*/version_code`）。免 Xposed 版即便不能真正"隐身"，也需要这套模型来描述"目标控件 + 目标状态 + 证据（截图/文本/层级）"。 |
| **三层容器** | `pkg → activityClass → List<ViewRule>`；等价于一个 SQLite 表 `(pkg, activity, idx)` 或 Room 三张表。 |
| **备份包格式** | 直接兼容原版：ZIP（后缀 `.gzip`）+ `manifest.json{version:1, packageName, rules:[...]}` + `<ms>.webp`，`img_path` 只存相对名。这样原版备份能导入我们的 App（我们只需忽略无法实现的 `visibility` 语义或降级为"遮挡"）。**注意**：恢复是 append 语义，且原版不校验 `version`，我们要加校验。 |
| **UI 流程** | 通用页（开关/加入组织/捐赠/进度）→ 应用列表（有规则的 App）→ 规则列表（备份/删除全部）→ 详情页（预览图 + 各字段 + 可编辑 alias）。preference key 可沿用（`editor_switch` 等）以便迁移 SharedPreferences。 |
| **长按选取交互** | `ACTION_DOWN` 起长按计时（`ViewConfiguration.getLongPressTimeout()`）→ 命中控件 → 半透明蒙版 + 可拖动 + 拖到底部取消区取消 + 松手"落规则" + 触觉反馈（`performHapticFeedback(0)`）。这套交互在我们的无障碍版里可以用「无障碍节点 + 自绘悬浮层」实现（见 7.3）。 |
| **配色/常量** | `MARK_COLOR=argb(0x96,0x8b,0xc3,0x4b)`、`OVERLAY_COLOR=argb(0xff,0,0,0)`、`ParticleView.PART_WH=8`、WEBP 质量 80、截图命名 `<ms>.webp`。 |

### 7.3 root + 无障碍 + 悬浮窗能做到什么程度

**能做的（按可靠度排序）**

1. **无障碍节点树 + 自绘蒙版做"选取与标注"**：`AccessibilityService.getWindows()` + `AccessibilityNodeInfo` 能拿到 `boundsInScreen`、`viewIdResourceName`、`className`、`text`、`contentDescription`、层级（通过 `getParent()` 链算 depth）。这足以**填满 `ViewRule` 的几乎所有字段**（`res_name`/`text`/`description`/`view_class`/边界/深度/`activityClass`）。→ 规则采集完全可行。
2. **`performAction(ACTION_CLICK)` / `ACTION_SCROLL`**：把"点一下"自动化，可以做"点掉广告位"式的操作型规则（与原版"屏蔽"语义不同，但对用户价值相当）。
3. **悬浮窗遮盖**：`TYPE_APPLICATION_OVERLAY`（需 `SYSTEM_ALERT_WINDOW`）在命中位置盖一层不透明色块/贴图，用 `FLAG_NOT_TOUCHABLE`（不挡操作）或可触摸（挡操作）两种模式。视觉上"消失"，本质是"遮住"。
4. **root 侧的增强（可选）**：
   - `setprop debug.layout true` + `ViewServer`/`uiautomator` 类 dump，能拿到更精确的层级与坐标；
   - 通过 `app_process` 注入一个 root 辅助进程做"截图/精确像素校验"，但**依然不能调目标进程的 View 方法**；
   - `pm disable` 之类的组件级禁用（对"整个 App 的某个入口"有效，对"App 内的某个按钮"无效）。
5. **截图 + 像素对比做"视觉验证"**：MediaProjection 截屏 → 按 `ViewRule.x/y/w/h` 裁剪 → 对比"规则应用前后"是否真的看不见（这是原版截图 webp 存在的意义），可用来自检规则是否仍匹配（App 升级后布局变了会失配）。

**做不到的 / 局限**

1. **不能真正 `GONE`/`INVISIBLE`**：控件仍在布局里，占位、仍响应无障碍、仍进截图的分析（除非遮盖）、仍会被 App 自己的逻辑使用。遮挡是"视觉"，不是"状态"。
2. **不能保证 `depth` 稳定**：无障碍树的 depth 与 View 树 depth 不等价（无障碍会合并/跳过节点），所以**不能直接套用原版规则里的 `depth` 做匹配**，必须靠 `res_name`+`text`+`class`+边界 加权匹配（`ViewHelper.findViewBestMatch` 的思路可以借，但特征权重需重算）。
3. **受无障碍能力边界限制**：WebView/Compose/Canvas 自绘控件在无障碍树里往往只有一个节点（无子节点），拿不到内部控件 → 这类界面只能整块遮。
4. **悬浮窗随时可能被系统杀/被用户关**：`SYSTEM_ALERT_WINDOW` 需手动授权，部分 ROM 会限制后台悬浮窗；覆盖层需要跟随窗口变化重算坐标（`AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED`/`TYPE_WINDOW_CONTENT_CHANGED` + `ViewTreeObserver` 思路不可用，只能靠事件回调重算）。
5. **安全/合规**：无障碍 + 悬浮窗做"自动化/遮蔽别人 App"在 Play 政策上是敏感用途；国内商店也要求说明用途。原版靠 Xposed 绕开了这些，我们绕不开。
6. **不能操作非 Activity 窗口**（原版也有限制，见 2.8）：输入法、系统弹窗、其他悬浮窗上的控件，无障碍能读但覆盖层层级可能冲突。

### 7.4 一句话给实现同学

> 我们做不出"从别人进程里移除 View"，但能做出"用无障碍精确识别控件 + 用悬浮窗视觉遮挡 + 用与原版**完全一致的规则模型/备份包格式**保存与迁移"，并且把原版最有价值的**长按选取 → 蒙版拖动 → 落规则**交互照搬过来；把 `visibility` 字段解释为"遮挡方式"（`4=透明占位遮挡`、`8=彻底遮住且吃掉触摸"），备份/恢复保持二进制兼容即可。
